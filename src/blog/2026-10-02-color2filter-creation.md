Style work on the [Stella Sora Wiki](https://stellasora.miraheze.org/wiki/Stella_Sora_Wiki) is something I have picked up recently and grown fond of. For some of the single-colour vendored images dumped from the game, I was interested in seeing if it was possible to recolour the images to put onto dynamic light and dark mode backgrounds. I searched around, and found the aformentioned tools.
However, all the web apps found gave a different result each time and were non deterministic. While this wasn't a major problem by any means, the problem intrigued me, and in nerd sniping fashion, I dove in.

A problem that developers run into is when they have icons, graphics, marketing images, or other single colour graphics that are not in a format to be recolourable. While it may be possible to go back and forth with designers and get them in a proper format, this can burn time, might be impossible if the assets in question are from a vendor that are not in their control.

Here's an example. A company website with a amber colour palette has a list of links in the footer that link to their different partners and socials. The design team wants to redesign this to match other websites, by replacing the list of links with icons of the company logos. Legal says that the icons must be loaded directly from a handful of companies' CDNs, as they don't have the legal rights to redistribute the images. Design hands you a Photoshop mockup of the design they have in mind. This isn't uncommon, as many companies have primarily print and media designers that do not have experience with vector tools like Figma. After handoff, you start recreating the design, and find out that the way Design "fixed" the vendored icons problem, was by adding a Colorize filter in Photoshop.

The web still doesn't have a built in "Colorize" or "Colour Overlay" filter for elements as of late 2026. To get around this problem, there are online tools, such as [angel-rs/css-color-filter-generator](https://angel-rs.github.io/css-color-filter-generator/) that can generate [CSS filters](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/filter) to recolour elements. This works well!
However, tools like the one that I have listed are indeterministic; they run a fixed number of iterations, using pseudo-random values to iteratively guess a CSS filter that is close enough to the original colour.

Try inputting the colour `#1fa82f` into the text field of css-color-filter-generator, and pressing the **Get Filter!** button again and again. While occassionally a 1:1 filter will be returned, most of the time, the colour will not be identical and require multi rerolls to get a perfect result. This isn't great for reproducibility, as every single person who tries to get a filter out of the same colour will get a different result.

So, I did some more research, and found an open source implementation of a deterministic CSS filter generator, using the COBYLA (Constrained Optimization BY Linear Approximation) algorithm by [ozwaldorf on GitHub](https://github.com/ozwaldorf). However, it was in Rust, and was embedded into a colour scheme specific tool, [Catppuccin Whiskers](https://github.com/ozwaldorf/whiskers/tree/feat/css_filter). 

I have almost zero experience with systems programming languges in actual projects, but I know a bit about Rust from one of the courses I took. So I decided to attempt splitting the code outside of Whiskers, and wrapping it into a CLI tool.
 

The changes needed were quite simple, but due to my inexperience, it took several hours to first setup Rust on a new devenv, understand the code, adapt the Whiskers specific types, and give it a CLI interface via [clap](https://docs.rs/clap/). I also wasted hours debugging, not realizing that the RGB values returned from [csscolorparser](https://docs.rs/csscolorparser/latest/csscolorparser/) were between 0-1, trying to figure out why the CSS filter outputs were pure black. 

The next day, I was thinking, what if I make a web app wrapper over this Rust code? How hard could it be? I did some more research and found out about WebAssembly, and how it could be used to run native code in the browser. I followed a tutorial to add WASM support to the Rust library, which wasn't too hard. Even though the commit adding support only shows a `+48` and `-17` LOC (lines of code) difference, this too, took me hours to figure out and implement in a clean way.

Now, the web app. It was very late at night after coming home that I decided to get started on this. So, I went with a completely new, completely unfamiliar tech stack for a side project that was not supposed to take up a lot of my free time. The web app is based on [Astro](https://astro.build/), [Tailwind CSS](https://tailwindcss.com/), and [Svelte](https://svelte.dev/). I had learned about these from various sources. Astro alongside Eleventy when I was choosing a tech stack while [creating this website](../2026-07-31-building-this-site/). Tailwind CSS from inspecting websites like Reddit and hearing about libraries like [shadcn](https://ui.shadcn.com/). And Svelte from inspecting websites like [Apple Music](https://music.apple.com/new) and [crates.io](https://crates.io/).

Now, even though I had heard of these, I had never actually worked with any of them in any projects. The only other, now deleted webapps I had built from the ground up were meme generators, and those used Vite + Lit + TypeScript. [l2d-viewer](https://github.com/ParasailNumerous/l2d-viewer) was originally built as a single file LLM slop mockup in CodePen, then migrated to the same stack as the meme generators.

So, at around 22:23, I dove in, bootstrapping the foundations for the app. This consisted of GitHub Pages and Dependabot, and the Svelte and Tailwind CSS integrations for Astro. Then, I once again got distracted, and hopped into Figma to design the logo for this web app ***before even making the web app that the logo was for***.

I experimented with several metaphors for representing a filter conversion tool like this. Some had real life photos with a 2-up, a code icon, a graphic of paint being spread over an image. The current design, a black circle with a palette icon on top, with the background being a 2-up of the hue wheel and example filter code was the best thing I could think of at the time. I am not likely to change it in the future, but it's not the best logo either. Even now, I can't think of a better way to represent that metaphor in a easy to read logo visible at all the sizes it needs to be at.

After completing the logo, still with no functional app in sight, I decided I would start working on it tomorrow. The next day, I setup some basic styling, added all the assets, a [webmanifest](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest) to make it a PWA, the configurations to make it work with GitHub Pages, and `<head>` tags. There was still no functional web app in sight. Maybe that's why I call myself a designer that learned to program to implement designs.

I spent about five hours, straight, with only a few breaks, working on the design of the app, entirely in the browser, just changing classes and watching it update in miliseconds. This loop has really grown on me, as it allows you to iterate very quickly on designs and try out different things. However, that sporadicness, and the lack of a unified place to put shared components and design system for a small project like this without introducing magnitudes of complexity is one downside. The Tailwind CSS official documentation suggests [multi-cursor editing](https://tailwindcss.com/docs/styling-with-utility-classes#using-multi-cursor-editing) as a solution to DRY (Don't Repeat Yourself) when you are not breaking things up into components, which I thought conflicted with many of the things I had learned. It hasn't grown on me, and the ergonomics are not great in my opinion, but maybe at some point, it will.

~19:30, design looks pretty, ***the app is still completely non-functional***. I had written it with stubs for the WASM part based on the wasm-pack documentation, which is why there is still misleading comments about beng able to regenerate the wrappers automatically.

I cloned the [Rust repository](https://github.com/ParasailNumerous/color2filter) into the `vendor` directory of the [web app repository](https://github.com/ParasailNumerous/color2filter-web) using `git clone`, and I didn't realize that it didn't count as a submodule. This will come up later. Then, I added a build script for wasm-pack derived from a StackOverflow post (Sorry, I don't remember which one) to the `package.json`, wired it up to the GitHub Actions, adding rustup and wasm-pack into the workflow. Then, I proceeded to get distracted iterating on the design again for another half hour.

After that distraction, again, I wrote a wrapper around the WASM JS bindings generated by wasm-pack, and wired it up to the Svelte component responsible for rendering the interactive elements. Another thing I ran into when making this. As an Astro newbie, I did not realize that for client-side JavaScript to be loaded, you need to add the `client:load` directive for it to be hydrated and functional. I spent much too long debugging why, thinking it was an error in the JavaScript itself.

After that, the app was finally functional! I pushed it to GitHub, and was immediately met with a build failure. The first one was because I forgot to enable GitHub Pages in the repository settings, but with the latest push, it was a still failing? Thankfully, with all my debugging experience from the past few hours, I figured out that my `git clone` didn't add the Rust repo for anything but my machine. After adding the submodule, the app was done!
